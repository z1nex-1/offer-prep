Второй тип «примитивов» из списка тем Яндекса — счётчики. Задачи звучат по-бэкендовому: «посчитать запросы за последние 5 минут», «не пускать пользователя чаще 10 раз в секунду», «показывать топ-10 запросов». В CodeRun такие задачи есть и в тренировках («Ограничитель частоты»), и в подборке собеседований в Городские сервисы («Счётчик запросов», «Наиболее загруженные рестораны»).

### Счётчик событий за последние N секунд

Операции: `hit(t)` — событие в момент t (моменты не убывают), `count(t)` — сколько событий было в полуинтервале `(t − N, t]`.

**Очередь времён.** Храним времена событий в `deque`. При `count(t)` выбрасываем из головы всё, что `≤ t − N`, и возвращаем длину.

```python
from collections import deque

class HitCounter:
    def __init__(self, window):
        self.window = window
        self.q = deque()

    def hit(self, t):
        self.q.append(t)

    def count(self, t):
        while self.q and self.q[0] <= t - self.window:
            self.q.popleft()
        return len(self.q)
```

Амортизированно O(1): каждое событие добавляется и удаляется один раз. Память — число событий в окне, может быть большим при высокой частоте.

**Кольцевой буфер по секундам.** Если времена целые и окно N секунд, храним N пар «секунда — счётчик». Событие в момент t попадает в ячейку `t % N`: если в ней записана другая секунда — счётчик обнуляется. `count` суммирует ячейки, чья секунда попадает в окно. Память O(N) независимо от частоты событий — так устроены многие счётчики в мониторинге.

```python
class BucketCounter:
    def __init__(self, window):
        self.n = window
        self.sec = [-1] * window
        self.cnt = [0] * window

    def hit(self, t):
        i = t % self.n
        if self.sec[i] != t:
            self.sec[i], self.cnt[i] = t, 0
        self.cnt[i] += 1

    def count(self, t):
        return sum(c for s, c in zip(self.sec, self.cnt) if t - self.n < s <= t)
```

### Топ-k самых частых в потоке

- Если нужно **точно** и данных немного: `Counter` плюс `heapq.nlargest(k, cnt.items(), key=...)` при каждом запросе — O(D log k), где D — число различных элементов.
- Если запросов топа много, а обновлений мало — держать отсортированную структуру.
- Если поток огромный и нужна **оценка**: Count-Min Sketch и алгоритмы вроде Space-Saving — приблизительные счётчики с фиксированной памятью. На собеседовании стажёра достаточно знать, что такие существуют.

При равных частотах условие обычно требует детерминированный порядок — например, лексикографический. Ключ сортировки `(-count, word)`.

### Rate limiting: четыре алгоритма

Задача: пропускать не больше R запросов за окно W для каждого клиента.

**Фиксированное окно.** Счётчик на текущий интервал `[kW, (k+1)W)`, при переходе в новый интервал обнуляется. Просто и дёшево (один счётчик), но на стыке окон пропускает до 2R запросов: R в конце одного окна и R в начале следующего.

**Журнал (sliding log).** Очередь времён запросов клиента, как в `HitCounter`: запрос проходит, если в очереди меньше R времён за последние W. Точно, но память O(R) на клиента.

**Скользящее окно со взвешиванием.** Два счётчика — текущего и предыдущего фиксированного окна; оценка `prev · (доля предыдущего окна, попавшая в скользящее) + cur`. Почти точно при O(1) памяти.

**Token bucket (ведро токенов).** Ведро ёмкостью B пополняется со скоростью r токенов в секунду; запрос забирает токен, если он есть, иначе отклоняется. Разрешает всплески до B запросов, а в среднем — r в секунду. Хранить нужно два числа: сколько токенов и когда пересчитывали; пополнение считается лениво при каждом запросе:

```python
class TokenBucket:
    def __init__(self, capacity, rate):
        self.cap, self.rate = capacity, rate
        self.tokens = capacity
        self.last = 0.0

    def allow(self, t):
        self.tokens = min(self.cap, self.tokens + (t - self.last) * self.rate)
        self.last = t
        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False
```

**Leaky bucket** — родственник: запросы встают в очередь и уходят с постоянной скоростью (как в задаче «Ограничитель частоты» — запросы складываются в очередь и отправляются не чаще заданного).

| | Точность | Память на клиента | Всплески |
|---|---|---|---|
| Фиксированное окно | до 2R на стыке | O(1) | да, на стыке |
| Журнал | точно | O(R) | нет |
| Скользящее со взвешиванием | почти точно | O(1) | почти нет |
| Token bucket | задаёт средний темп | O(1) | до B, управляемо |

В распределённой системе счётчики хранят в Redis (атомарные `INCR` с `EXPIRE` или Lua-скрипты), чтобы все копии сервиса видели общий лимит. При превышении отвечают `429 Too Many Requests` с заголовком `Retry-After`.

### Типичные ошибки

- Граница окна: `<` против `<=` при выбрасывании старых событий — окно на секунду шире или уже.
- Пересчёт окна полным проходом по всем событиям при каждом запросе — O(n) на операцию.
- Token bucket с пополнением «по таймеру» в отдельном потоке вместо ленивого пересчёта.
- Фиксированное окно там, где важно не пропускать 2R на стыке.
- Отсутствие детерминированного порядка при равных частотах в топ-k.

## Вопросы на собеседовании

### Как посчитать число запросов за последние 5 минут?
Очередь времён: добавляем время нового запроса, перед подсчётом удаляем из головы всё старше t − 300, размер очереди — ответ; амортизированно O(1), память — число запросов в окне. Если запросов очень много, а точность до секунды достаточна — кольцевой буфер на 300 ячеек «секунда — счётчик», память O(300).

### Как бы вы сделали rate limiter для API?
Выбрал бы token bucket на клиента: ёмкость задаёт допустимый всплеск, скорость пополнения — средний лимит, состояние — два числа, пополнение лениво при запросе. В распределённом сервисе состояние хранится в Redis с атомарным обновлением. При превышении — 429 с Retry-After. Если нужен строгий лимит без всплесков — журнал или скользящее окно со взвешиванием.
