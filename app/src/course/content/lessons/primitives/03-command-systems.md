В треке «Бэкенд» на CodeRun много задач одного жанра: на вход приходит поток команд — «пополнить счёт», «обновить товар», «откатить транзакцию», — и нужно реализовать систему, которая их выполняет. Примеры: «Банковские счета» из тренировок Яндекса, «Сервис подписки» и «Коля и датацентры» из задач трека бэкенда, «Листы и вью». Алгоритм в них обычно простой, а сложность — в аккуратности и в выборе структур.

### Метод

1. **Выпишите все команды** и что каждая возвращает. Отдельно — поведение в особых случаях (нет клиента, пустой стек, откат без транзакции).
2. **Для каждой команды — требуемая сложность** при данных ограничениях. Операции в цикле по всем клиентам на каждой команде — частая причина TL.
3. **Выберите состояние**: какие словари, списки, кучи. Иногда нужна «ленивая» операция: вместо изменения всех записей хранить общий множитель или версию.
4. **Разбор ввода отдельно от логики**: `cmd, *args = line.split()` и словарь обработчиков или цепочка `if`.
5. **Вывод — в список**, печать одним `join` в конце.

```python
import sys

def main():
    out = []
    balance = {}
    for line in sys.stdin.read().splitlines():
        cmd, *args = line.split()
        if cmd == "DEPOSIT":
            name, s = args[0], int(args[1])
            balance[name] = balance.get(name, 0) + s
        elif cmd == "BALANCE":
            out.append(str(balance[args[0]]) if args[0] in balance else "ERROR")
        # ...
    print("\n".join(out))

main()
```

### Хранилище с версиями по времени

Команды: `SET key value t` (времена для одного ключа возрастают) и `GET key t` — значение ключа, установленное в последний момент ≤ t.

Для каждого ключа храним два списка — времена и значения — в порядке добавления. Времена возрастают, значит, `GET` — бинпоиск:

```python
from bisect import bisect_right

times, values = {}, {}

def set_(key, value, t):
    times.setdefault(key, []).append(t)
    values.setdefault(key, []).append(value)

def get(key, t):
    ts = times.get(key)
    if not ts:
        return None
    i = bisect_right(ts, t) - 1
    return values[key][i] if i >= 0 else None
```

`SET` — O(1), `GET` — O(log n). Так же устроены многоверсионные хранилища (MVCC в базах данных из урока о транзакциях): каждая запись помнит, с какого момента она актуальна.

### Снимки массива

Команды: `SET i v`, `SNAP` (сделать снимок, вернуть его номер), `GET i snap_id` (значение элемента i в снимке). Копировать весь массив при каждом `SNAP` — O(n) памяти и времени на снимок.

Идея та же: для каждого индекса хранить историю изменений `(номер снимка, значение)`. `SET` пишет в текущий снимок (перезаписывая, если в этом снимке уже меняли), `GET` находит бинпоиском последнее изменение с номером ≤ snap_id. `SNAP` — O(1).

### Вложенные транзакции

Команды хранилища: `SET key value`, `GET key`, `UNSET key`, `BEGIN`, `ROLLBACK` (откатить последнюю открытую транзакцию), `COMMIT` (зафиксировать все открытые).

Решение — **журнал отката**: стек транзакций, в каждой — список «как вернуть обратно»: для каждого изменённого ключа его прежнее значение (или отметка, что ключа не было). `ROLLBACK` проходит журнал последней транзакции в обратном порядке и восстанавливает значения. `COMMIT` просто очищает стек.

```python
store = {}
MISSING = object()
tx = []                 # стек журналов

def set_(k, v):
    if tx:
        tx[-1].append((k, store.get(k, MISSING)))
    store[k] = v

def rollback():
    if not tx:
        return "NO TRANSACTION"
    for k, old in reversed(tx.pop()):
        if old is MISSING:
            store.pop(k, None)
        else:
            store[k] = old
```

Альтернатива — стек словарей-«слоёв»: чтение ищет ключ сверху вниз. Журнал удобнее, если чтений много: `GET` остаётся O(1).

Это модель того, как базы данных делают `ROLLBACK`: журнал изменений позволяет вернуть состояние.

### Ленивые массовые операции

Если команда меняет **все** записи сразу («начислить всем проценты», «сдвинуть все цены»), обновлять каждую — O(n) на команду. Иногда можно хранить **общий множитель или сдвиг** и учитывать его при чтении и записи: запись хранится как «значение в масштабе на момент записи», а при чтении умножается на накопленный множитель. Но с округлениями (проценты на копейки) такая ленивость ломается — тогда честный проход по всем клиентам, если их немного, как в «Банковских счетах», где ограничения это позволяют. Смотрите на ограничения.

### Типичные ошибки

- Особый случай из условия не обработан: снятие больше остатка, перевод самому себе, клиент ещё не существует.
- Разбор строк с лишними пробелами или пустыми строками в конце ввода.
- Операция «для всех» на каждой команде при больших ограничениях.
- В журнале транзакций не запомнено, что ключа не было, — после отката остаётся лишний ключ.
- Печать по одной строке в цикле на 10⁵ команд.

## Самопроверка

### Как хранить историю ключа, чтобы `GET key t` работал за O(log n)?
- [ ] Копировать всё хранилище при каждом SET
- [x] Для ключа — список времён по возрастанию и список значений; GET — бинпоиск по времени
- [ ] Пересчитывать по всем командам
- [ ] Хранить только последнее значение
> Времена возрастают, поэтому `bisect_right(times, t) - 1` даёт последнее изменение не позже t.

### Что выведет код?
```python
from bisect import bisect_right
ts, vs = [1, 4, 9], ["a", "b", "c"]
res = []
for t in [0, 4, 8, 20]:
    i = bisect_right(ts, t) - 1
    res.append(vs[i] if i >= 0 else "-")
print(" ".join(res))
```
- [ ] `- a b c`
- [x] `- b b c`
- [ ] `a b b c`
- [ ] `- b c c`
> До момента 1 значения нет; в 4 и 8 актуально значение из момента 4; в 20 — из момента 9.

### Что нужно записать в журнал отката при SET внутри транзакции?
- [ ] Новое значение
- [x] Прежнее значение ключа или отметку, что ключа не было
- [ ] Номер команды
- [ ] Ничего
> ROLLBACK восстанавливает прежние значения в обратном порядке.

### Почему `SNAP` не должен копировать весь массив?
- [ ] Копирование запрещено в Python
- [x] Копия — O(n) времени и памяти на каждый снимок; достаточно хранить историю изменений индексов
- [ ] Снимки не нужны
- [ ] Массив слишком маленький
> История изменений даёт O(1) на снимок и O(log) на чтение.

### Как быстро вывести ответы на 10⁵ команд?
- [ ] print в каждой команде
- [x] Собрать строки в список и напечатать один раз через join
- [ ] Записать в файл
- [ ] Выводить только последние
> Один вывод в разы быстрее ста тысяч вызовов print.

## Вопросы на собеседовании

### Как реализовать хранилище ключ-значение с поддержкой вложенных транзакций?
Основной словарь плюс стек журналов отката — по одному на открытую транзакцию. При изменении внутри транзакции в её журнал пишется прежнее значение ключа (или отметка «ключа не было»). ROLLBACK извлекает последний журнал и восстанавливает значения в обратном порядке. COMMIT очищает стек. GET и SET остаются O(1), ROLLBACK — O(числа изменений в транзакции).

### Как вернуть значение ключа на произвольный момент времени?
Хранить для ключа историю изменений в порядке времени — список моментов и список значений. Запрос на момент t — бинпоиск последнего изменения с временем ≤ t. Запись O(1) при возрастающих временах, чтение O(log n). Так устроены многоверсионные хранилища.
