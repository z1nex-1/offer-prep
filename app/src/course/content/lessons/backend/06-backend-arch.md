### Путь запроса

```
клиент → DNS → балансировщик (L4/L7) → веб-сервер / reverse proxy (nginx)
       → приложение (несколько копий) → кэш (Redis) → база данных (мастер + реплики)
                                      → очередь (Kafka, RabbitMQ) → фоновые обработчики
```

- **Балансировщик** распределяет запросы между копиями приложения (по кругу, по наименьшей загрузке, по хешу клиента), снимает с потока упавшие копии по проверкам здоровья (health check).
- **Reverse proxy** (nginx) принимает соединения, завершает TLS, раздаёт статику, сжимает ответы, буферизует медленных клиентов.
- **Приложение** — ваш код на Python.

### WSGI и ASGI

Python-приложение не слушает сеть само — его запускает сервер приложений:

- **WSGI** — синхронный стандарт: сервер вызывает функцию `app(environ, start_response)` на каждый запрос. Серверы — gunicorn, uWSGI; фреймворки — Django, Flask. Параллельность — несколькими процессами и потоками.
- **ASGI** — асинхронный стандарт: `async def app(scope, receive, send)`, поддерживает WebSocket и тысячи одновременных соединений в одном процессе. Серверы — uvicorn, hypercorn; фреймворки — FastAPI, Starlette, Django в асинхронном режиме.

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/users/{user_id}")
async def get_user(user_id: int):
    return {"id": user_id}
```

Типичный запуск: `gunicorn -k uvicorn.workers.UvicornWorker -w 4 app:app` — 4 процесса-воркера (по числу ядер), в каждом — асинхронный цикл.

### Горизонтальное масштабирование

- **Вертикальное** — более мощный сервер; упирается в потолок и цену.
- **Горизонтальное** — больше одинаковых серверов за балансировщиком.

Чтобы добавлять копии приложения свободно, оно должно быть **stateless**: не хранить состояние пользователя в памяти процесса. Сессии — в Redis или в токене, файлы — в объектном хранилище, данные — в базе. Тогда любой запрос может обработать любая копия.

### Кэширование

Кэш хранит результат дорогой операции, чтобы не повторять её:

- в процессе (`functools.lru_cache`) — быстро, но у каждой копии свой;
- распределённый (Redis, Memcached) — общий для всех копий;
- HTTP-кэш и CDN — на стороне клиента и граничных серверов.

Стратегии:

- **cache-aside**: приложение сначала смотрит в кэш, при промахе читает базу и кладёт результат в кэш с TTL — самая распространённая;
- **write-through**: запись идёт в кэш и базу сразу;
- **write-back**: запись в кэш, в базу — позже пачками (быстро, но риск потери).

Главная трудность — **инвалидация**: после изменения данных кэш должен обновиться или удалиться, иначе пользователи видят устаревшее. Простые приёмы — TTL, удаление ключа при записи. Проблемы: **cache stampede** (ключ истёк, и тысяча запросов одновременно идёт в базу — лечат блокировкой на пересчёт или ранним обновлением), вытеснение (LRU — реализация есть в модуле «Примитивы»).

### Очереди сообщений

Не всё нужно делать во время запроса. Отправка письма, пересчёт рекомендаций, обработка видео уходят в **очередь**: API кладёт задачу и сразу отвечает, фоновые обработчики забирают задачи.

- **RabbitMQ** — классический брокер сообщений: очереди, подтверждения, маршрутизация.
- **Kafka** — распределённый журнал: сообщения хранятся и читаются многими потребителями, высокая пропускная способность, порядок внутри раздела.
- Гарантии доставки: «не больше одного раза», «хотя бы один раз» (самая частая — обработчики должны быть **идемпотентными**, чтобы повтор не навредил), «ровно один раз» (дорого и с оговорками).

Очереди сглаживают пики нагрузки и развязывают сервисы: если обработчик упал, задачи подождут.

### Ограничение частоты запросов

Rate limiting защищает сервис от перегрузки и злоупотреблений: «не больше 100 запросов в минуту на пользователя». Алгоритмы: фиксированное окно (счётчик на минуту), скользящее окно (очередь времён или взвешенные окна), **token bucket** (ведро токенов пополняется с постоянной скоростью, запрос забирает токен). Превышение — ответ 429. Реализация на Redis — атомарные `INCR` и `EXPIRE`.

### Монолит и микросервисы

**Монолит** — одно приложение: проще разрабатывать, тестировать и деплоить на старте. **Микросервисы** — много небольших сервисов, каждый со своей базой и командой, общаются по HTTP или gRPC и через очереди. Плюсы: независимые деплой и масштабирование, изоляция сбоев. Минусы: сетевые вызовы, распределённые транзакции, сложная отладка. Нужны таймауты, повторы с экспоненциальной задержкой и circuit breaker, чтобы сбой одного сервиса не обрушил цепочку.

### Наблюдаемость

- **Логи** — события с контекстом (идентификатор запроса), собираются централизованно.
- **Метрики** — числа во времени: RPS, доля ошибок, время ответа (перцентили p50, p95, p99 — среднее прячет медленные запросы), нагрузка на CPU и память. Prometheus и Grafana.
- **Трассировка** — путь одного запроса через все сервисы.
- **Алерты** — сигнал дежурному, когда метрика выходит за порог.

### Контейнеры и деплой

**Docker** упаковывает приложение с зависимостями в образ, который одинаково запускается везде. `Dockerfile` описывает сборку, `docker-compose` — несколько сервисов локально (приложение, база, Redis). **Kubernetes** управляет контейнерами на кластере: разворачивает копии, перезапускает упавшие, масштабирует. **CI/CD** — автоматические тесты и выкладка при каждом изменении.

### P2P на примере BitTorrent

BitTorrent упомянут в списке протоколов на странице бэкенд-стажировки Яндекса. Это пример одноранговой (P2P) системы: файл разбит на куски с хешами, участники (пиры) скачивают куски друг у друга и одновременно раздают скачанное. Трекер или распределённая хеш-таблица (DHT) помогают найти пиров. Сначала качают самые редкие куски, чтобы они не пропали из сети. Нагрузка распределяется между участниками вместо одного сервера. Тот же принцип «раздают все, кто скачал» используется при раздаче больших файлов по многим серверам внутри дата-центров.

### Мини-проектирование: сокращатель ссылок

Если попросят «спроектируйте сервис коротких ссылок», идите по шагам:

1. **Требования**: создать короткую ссылку, перейти по ней (редирект 301/302), срок жизни, статистика; чтений намного больше, чем записей.
2. **API**: `POST /links {url}` → `{short}`, `GET /{short}` → редирект.
3. **Генерация ключа**: счётчик в базе, переведённый в base62 (7 символов — 62⁷ ≈ 3,5·10¹² ссылок), или случайная строка с проверкой коллизии.
4. **Хранение**: таблица `short → url`, индекс по `short` (первичный ключ).
5. **Нагрузка**: чтения — через кэш (Redis) с LRU, CDN для самых популярных; реплики базы для чтения.
6. **Статистика**: события переходов — в очередь и в аналитическую базу (например, ClickHouse), а не синхронной записью в основную.

### Типичные ошибки

- Хранить сессии в памяти процесса и удивляться, что после масштабирования пользователей «разлогинивает».
- Кэш без TTL и без инвалидации.
- Долгие операции внутри обработчика запроса вместо фоновой очереди.
- Повторы запросов без таймаутов и идемпотентности.
- Судить о скорости сервиса по среднему времени ответа, а не по перцентилям.

### Как спрашивают на Яндексе

На странице бэкенд-стажировки среди преимуществ — «опыт параллельных или распределённых вычислений» и сетевые протоколы. На секциях Intern week offer архитектура — не отдельная секция (отдельная архитектурная секция описана в Week Offer для опытных бэкенд-разработчиков, не для стажёров), но вопросы о кэше, очередях и масштабировании звучат на встречах с командами: там рассказывают о своих сервисах и спрашивают о ваших проектах. ## Вопросы на собеседовании

### Что происходит с запросом от клиента до базы данных в типичном веб-сервисе?
DNS даёт адрес балансировщика; балансировщик выбирает здоровую копию приложения; reverse proxy завершает TLS и передаёт запрос серверу приложений (gunicorn или uvicorn), тот вызывает код фреймворка. Приложение проверяет авторизацию, смотрит в кэш, при промахе обращается к базе (запись — в мастер, чтение — возможно, в реплику), тяжёлую работу откладывает в очередь и возвращает ответ.

### Зачем нужен кэш и какие с ним проблемы?
Чтобы не повторять дорогие операции: запросы к базе, вызовы других сервисов, вычисления. Проблемы: устаревшие данные (нужна инвалидация или TTL), одновременный пересчёт истёкшего популярного ключа (cache stampede), вытеснение при нехватке памяти (LRU), согласованность между кэшем и базой при записи.

### Когда стоит использовать очередь сообщений?
Когда работа не нужна для ответа пользователю (письма, уведомления, пересчёты), когда нужно сгладить пики нагрузки, развязать сервисы или гарантировать выполнение при временном сбое обработчика. Обработчики делают идемпотентными, потому что сообщение может прийти повторно.

### Как спроектировать сервис коротких ссылок?
Уточнить требования и нагрузку, описать API создания и перехода, выбрать генерацию ключа (счётчик в base62 или случайная строка с проверкой), хранить пару ключ → URL с индексом по ключу, чтения обслуживать через кэш и реплики, статистику переходов писать асинхронно через очередь в аналитическое хранилище.
