### Реляционная модель

Данные хранятся в **таблицах**: строки — записи, столбцы — атрибуты с типами.

- **Первичный ключ** (primary key) — столбец или набор столбцов, однозначно определяющий строку (`id`).
- **Внешний ключ** (foreign key) — ссылка на первичный ключ другой таблицы (`orders.user_id → users.id`); база не даст сослаться на несуществующего пользователя.
- **Связи**: один-к-одному, один-ко-многим (пользователь → заказы), многие-ко-многим — через промежуточную таблицу (`order_items(order_id, product_id)`).

Пример схемы, на которой разберём запросы:

```sql
users(id, name, city)
orders(id, user_id, created_at, amount)
```

### SELECT по шагам

```sql
SELECT city, COUNT(*) AS users_cnt
FROM users
WHERE name LIKE 'А%'
GROUP BY city
HAVING COUNT(*) > 10
ORDER BY users_cnt DESC
LIMIT 5;
```

**Логический порядок выполнения** отличается от порядка записи — это любимый вопрос:

1. `FROM` (и `JOIN`) — откуда берём строки;
2. `WHERE` — фильтр строк;
3. `GROUP BY` — группировка;
4. `HAVING` — фильтр групп;
5. `SELECT` — вычисление столбцов и псевдонимов;
6. `DISTINCT`;
7. `ORDER BY` — сортировка (тут псевдонимы уже доступны);
8. `LIMIT` / `OFFSET`.

Отсюда: в `WHERE` нельзя использовать агрегаты (`WHERE COUNT(*) > 10` — ошибка, нужен `HAVING`) и, в большинстве СУБД, псевдонимы из `SELECT`.

### JOIN

```sql
SELECT u.name, o.amount
FROM users u
JOIN orders o ON o.user_id = u.id;
```

| Вид | Что вернёт |
|---|---|
| `INNER JOIN` | только пары, где условие выполнено |
| `LEFT JOIN` | все строки левой таблицы; где пары нет — `NULL` справа |
| `RIGHT JOIN` | зеркально |
| `FULL JOIN` | все строки обеих, недостающее — `NULL` |
| `CROSS JOIN` | все пары (декартово произведение) |

Классика: «пользователи без заказов» —

```sql
SELECT u.*
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;
```

Ловушка: условие на правую таблицу в `WHERE` после `LEFT JOIN` превращает его в `INNER JOIN` — строки с `NULL` отфильтруются. Такое условие нужно писать в `ON`.

Если в правой таблице несколько совпадений, строка левой **размножится** — поэтому `SUM` после `JOIN` может посчитать суммы многократно.

### Агрегаты и группировка

`COUNT(*)` — число строк, `COUNT(col)` — число не-NULL значений, `COUNT(DISTINCT col)` — различных, `SUM`, `AVG`, `MIN`, `MAX`. В `SELECT` с `GROUP BY` можно выводить только столбцы группировки и агрегаты.

```sql
-- средний чек и число заказов по городам, только города с выручкой больше миллиона
SELECT u.city, COUNT(o.id) AS orders_cnt, AVG(o.amount) AS avg_check
FROM users u
JOIN orders o ON o.user_id = u.id
GROUP BY u.city
HAVING SUM(o.amount) > 1000000;
```

### NULL

`NULL` — «значение неизвестно». Любое сравнение с ним даёт `NULL` (не `TRUE` и не `FALSE`):

- `WHERE x = NULL` не найдёт ничего — нужно `WHERE x IS NULL`;
- `NOT IN (подзапрос)`, где в подзапросе есть `NULL`, вернёт пустой результат — безопаснее `NOT EXISTS`;
- агрегаты (кроме `COUNT(*)`) игнорируют `NULL`;
- `COALESCE(x, 0)` подставляет значение по умолчанию.

### Подзапросы и CTE

```sql
-- пользователи, у которых есть заказ дороже 10000
SELECT name FROM users
WHERE id IN (SELECT user_id FROM orders WHERE amount > 10000);

-- то же через EXISTS (часто эффективнее и безопаснее с NULL)
SELECT name FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id AND o.amount > 10000);

-- CTE: именованный подзапрос для читаемости
WITH user_totals AS (
    SELECT user_id, SUM(amount) AS total FROM orders GROUP BY user_id
)
SELECT u.name, t.total FROM users u JOIN user_totals t ON t.user_id = u.id
ORDER BY t.total DESC LIMIT 10;
```

### Оконные функции

Считают значение по «окну» строк, **не схлопывая** их в одну, как `GROUP BY`:

```sql
SELECT user_id, created_at, amount,
       ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at) AS order_no,
       SUM(amount)  OVER (PARTITION BY user_id ORDER BY created_at) AS running_total
FROM orders;
```

- `ROW_NUMBER`, `RANK`, `DENSE_RANK` — нумерация внутри группы (`RANK` оставляет пропуски при равенстве, `DENSE_RANK` — нет);
- `LAG(x)`, `LEAD(x)` — значение из предыдущей или следующей строки (интервалы между заказами);
- агрегаты с `OVER` — накопительные суммы, средние по окну.

Классика «топ-1 в каждой группе»: пронумеровать `ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ... DESC)` и оставить строки с номером 1.

### Изменение данных

```sql
INSERT INTO users (name, city) VALUES ('Аня', 'Москва');
UPDATE orders SET amount = amount * 0.9 WHERE created_at < '2026-01-01';
DELETE FROM orders WHERE amount = 0;
```

`UPDATE` и `DELETE` без `WHERE` меняют всю таблицу — на собеседовании про это любят спросить в шутку, а на работе это настоящая авария.

### Типичные ошибки

- Агрегат в `WHERE` вместо `HAVING`.
- `= NULL` вместо `IS NULL`; `NOT IN` с `NULL` в подзапросе.
- Условие на правую таблицу `LEFT JOIN` в `WHERE`.
- Размножение строк при `JOIN` перед агрегацией.
- Столбец в `SELECT`, которого нет в `GROUP BY` и который не агрегирован.

### Как спрашивают на Яндексе

На бэкенд-секциях SQL обычно всплывает в теоретических вопросах: виды JOIN, разница WHERE и HAVING, порядок выполнения запроса, а также индексы и транзакции (следующий урок). ## Самопроверка

### В каком порядке логически выполняются части запроса?
- [ ] SELECT → FROM → WHERE → GROUP BY
- [x] FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
- [ ] FROM → SELECT → WHERE → ORDER BY
- [ ] WHERE → FROM → GROUP BY → SELECT
> Поэтому агрегаты фильтруют в HAVING, а псевдонимы доступны в ORDER BY.

### Как найти пользователей без заказов?
- [ ] `INNER JOIN orders` и `WHERE orders.id IS NULL`
- [x] `LEFT JOIN orders ... WHERE orders.id IS NULL`
- [ ] `WHERE orders = NULL`
- [ ] `GROUP BY user_id HAVING COUNT(*) = 0` по таблице orders
> LEFT JOIN сохраняет пользователей без пары, у них столбцы заказа — NULL.

### Что вернёт `SELECT * FROM t WHERE x = NULL`?
- [ ] Строки, где x пустой
- [x] Ничего: сравнение с NULL даёт NULL, а не TRUE
- [ ] Все строки
- [ ] Ошибку синтаксиса
> Проверка на NULL — `IS NULL`.

### Чем HAVING отличается от WHERE?
- [ ] Ничем
- [x] WHERE фильтрует строки до группировки, HAVING — группы после неё, можно использовать агрегаты
- [ ] HAVING работает только с JOIN
- [ ] WHERE работает только с числами
> `HAVING COUNT(*) > 10` — фильтр по результату агрегации.

### Чем оконная функция отличается от GROUP BY?
- [ ] Ничем
- [x] Считает значение по группе строк, но не схлопывает их — каждая строка остаётся в результате
- [ ] Работает только с датами
- [ ] Не поддерживает сортировку
> Например, накопительная сумма заказов для каждой строки.

### Какой вид JOIN вернёт все строки обеих таблиц, заполняя недостающее NULL?
- [ ] INNER
- [ ] LEFT
- [x] FULL
- [ ] CROSS
> CROSS JOIN возвращает все пары строк — декартово произведение.

## Вопросы на собеседовании

### Какие бывают JOIN и чем они отличаются?
INNER — только совпавшие пары. LEFT — все строки левой таблицы, для несовпавших справа NULL; RIGHT — зеркально. FULL — все строки обеих. CROSS — декартово произведение. Важно: при нескольких совпадениях строки размножаются, а условие на правую таблицу LEFT JOIN в WHERE превращает его в INNER.

### Чем WHERE отличается от HAVING?
WHERE фильтрует строки до группировки и не видит агрегатов. HAVING фильтрует группы после GROUP BY и может использовать агрегаты. По возможности фильтр ставят в WHERE — меньше строк попадает в группировку.

### Что такое NULL и какие с ним проблемы?
Отметка «значение неизвестно». Сравнения с NULL дают NULL, поэтому проверяют через IS NULL; NOT IN с NULL в подзапросе ничего не возвращает; агрегаты игнорируют NULL (кроме COUNT(*)); в уникальных индексах NULL обычно не считаются равными. COALESCE подставляет значение по умолчанию.

### Как вывести топ-3 товара по продажам в каждой категории?
Посчитать продажи по товарам, пронумеровать внутри категории оконной функцией `ROW_NUMBER() OVER (PARTITION BY category ORDER BY sales DESC)` в CTE или подзапросе и оставить строки с номером ≤ 3. Если равные продажи должны делить место — `DENSE_RANK`.
