### Запрос и ответ

HTTP — текстовый (в версии 1.1) протокол «запрос — ответ» поверх TCP. Запрос:

```
POST /api/orders HTTP/1.1
Host: shop.example.com
Content-Type: application/json
Authorization: Bearer eyJhbGciOi...
Content-Length: 39

{"product_id": 42, "quantity": 2}
```

Ответ:

```
HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/orders/1001

{"id": 1001, "status": "created"}
```

Стартовая строка, заголовки, пустая строка, тело. HTTP **не хранит состояние** между запросами (stateless): всё, что серверу нужно знать о клиенте, передаётся в каждом запросе — cookie, токен.

### Методы

| Метод | Смысл | Безопасный | Идемпотентный | Тело запроса |
|---|---|---|---|---|
| GET | получить ресурс | да | да | нет |
| HEAD | как GET, только заголовки | да | да | нет |
| POST | создать или выполнить действие | нет | **нет** | да |
| PUT | заменить ресурс целиком | нет | да | да |
| PATCH | изменить часть ресурса | нет | не обязательно | да |
| DELETE | удалить | нет | да | обычно нет |
| OPTIONS | какие методы доступны (CORS) | да | да | нет |

- **Безопасный** — не меняет состояние сервера (только чтение).
- **Идемпотентный** — повтор запроса даёт тот же результат, что и один запрос. Важно для повторов при сетевых сбоях: GET, PUT, DELETE можно безопасно повторить, POST — нет (создастся второй заказ). Для POST делают ключ идемпотентности: клиент передаёт уникальный `Idempotency-Key`, сервер не выполняет запрос с тем же ключом дважды.

### Коды ответов

| Класс | Смысл | Частые коды |
|---|---|---|
| 1xx | информационные | 101 Switching Protocols (WebSocket) |
| 2xx | успех | 200 OK, 201 Created, 204 No Content |
| 3xx | перенаправление | 301 Moved Permanently, 302 Found, 304 Not Modified |
| 4xx | ошибка клиента | 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 422 Unprocessable Entity, 429 Too Many Requests |
| 5xx | ошибка сервера | 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout |

Частые вопросы: **401 или 403** — 401 значит «не знаю, кто вы» (нет или неверные учётные данные), 403 — «знаю, но нельзя». **502 или 504** — прокси получил от сервера некорректный ответ или не получил ответа вовремя.

### Заголовки

- `Host` — какой сайт на этом IP (обязателен в HTTP/1.1);
- `Content-Type`, `Content-Length` — тип и длина тела;
- `Accept`, `Accept-Encoding` — что клиент умеет принимать (например, gzip);
- `Authorization` — учётные данные;
- `Cookie` / `Set-Cookie` — хранение состояния на клиенте;
- `Cache-Control`, `ETag`, `If-None-Match` — кэширование: если ресурс не изменился, сервер отвечает 304 без тела;
- `Location` — куда перенаправлять или где созданный ресурс;
- `Access-Control-Allow-Origin` — CORS: каким сайтам браузер разрешит читать ответ.

### Cookies, сессии и токены

- **Сессия на сервере**: при входе сервер создаёт запись сессии и отдаёт её идентификатор в cookie (`Set-Cookie: sid=...; HttpOnly; Secure; SameSite=Lax`). Каждый запрос приносит cookie, сервер находит сессию в хранилище.
- **Токен (JWT)**: сервер выдаёт подписанный токен с данными пользователя и сроком жизни, клиент шлёт его в `Authorization: Bearer ...`. Серверу не нужно хранилище сессий — достаточно проверить подпись. Минус — сложно отозвать токен до истечения срока.
- **Аутентификация** — кто вы; **авторизация** — что вам можно.

### HTTPS и TLS

HTTPS — HTTP поверх TLS. TLS даёт **шифрование** (никто в сети не читает трафик), **целостность** (никто не подменит данные незаметно) и **аутентификацию сервера** (сертификат, подписанный удостоверяющим центром, которому доверяет браузер). При рукопожатии стороны с помощью асимметричной криптографии договариваются об общем сеансовом ключе, дальше данные шифруются симметрично — это быстро.

### Версии HTTP

- **HTTP/1.1** — текст, одно соединение обрабатывает запросы последовательно; браузеры открывают по 6 соединений на сайт; keep-alive переиспользует соединение.
- **HTTP/2** — бинарный, **мультиплексирование**: много запросов параллельно в одном TCP-соединении, сжатие заголовков. Но потеря одного TCP-пакета задерживает все потоки.
- **HTTP/3** — поверх QUIC (UDP), независимые потоки, быстрее установка соединения.

### REST

REST — архитектурный стиль API поверх HTTP:

- **ресурсы** адресуются URL: `/users`, `/users/42`, `/users/42/orders`;
- **действия** выражаются методами: `GET /users/42`, `DELETE /users/42`, `POST /users`;
- **stateless**: каждый запрос самодостаточен;
- ответы используют коды HTTP по смыслу;
- представление — обычно JSON.

Хорошие практики: существительные во множественном числе в путях, пагинация (`?limit=20&cursor=...`), фильтры в query-параметрах, версионирование (`/v1/...`), понятные коды ошибок и тело ошибки с сообщением.

### gRPC

gRPC — фреймворк удалённого вызова процедур от Google, популярный для общения микросервисов:

- контракт описывается в `.proto`-файле, по нему генерируется клиент и сервер для разных языков;
- данные сериализуются в **Protocol Buffers** — компактный бинарный формат, в разы меньше и быстрее JSON;
- работает поверх HTTP/2, поддерживает потоковую передачу в обе стороны;
- строгая типизация контракта и обратная совместимость полей по номерам.

```proto
service OrderService {
  rpc GetOrder (GetOrderRequest) returns (Order);
}
message GetOrderRequest { int64 id = 1; }
message Order { int64 id = 1; string status = 2; }
```

REST — для публичных API и браузера (просто, человекочитаемо). gRPC — для внутреннего взаимодействия сервисов (быстро, строгие контракты, стриминг).

### WebSocket

Постоянное двустороннее соединение поверх TCP: начинается с HTTP-запроса `Upgrade: websocket`, дальше сервер может сам отправлять клиенту сообщения. Для чатов, уведомлений, совместного редактирования. Альтернативы — long polling и Server-Sent Events.

### Типичные ошибки на собеседовании

- Говорить, что POST идемпотентен, или путать безопасность и идемпотентность.
- Путать 401 и 403, 502 и 504.
- Утверждать, что HTTPS шифрует и адрес сайта: имя хоста видно в DNS и в SNI (если не используется ECH).
- Считать REST протоколом, а не стилем.

## Вопросы на собеседовании

### Что такое идемпотентность и какие HTTP-методы идемпотентны?
Повтор запроса приводит к тому же состоянию, что и одиночный. Идемпотентны GET, HEAD, PUT, DELETE, OPTIONS; POST — нет, PATCH — не обязательно. Это важно для повторов при таймаутах: идемпотентный запрос можно повторить без риска, а для POST нужен ключ идемпотентности, по которому сервер распознаёт повтор.

### Чем REST отличается от gRPC?
REST — стиль API поверх HTTP: ресурсы в URL, действия методами HTTP, обычно JSON, человекочитаем и работает из браузера. gRPC — RPC-фреймворк с контрактом в `.proto`, генерацией кода, бинарным Protobuf поверх HTTP/2 и стримингом; быстрее и строже, удобен для межсервисного взаимодействия.

### Как работает HTTPS?
Поверх TCP устанавливается TLS-соединение: клиент и сервер согласуют версию и шифры, сервер предъявляет сертификат, клиент проверяет подпись удостоверяющего центра и совпадение имени, стороны вырабатывают общий симметричный ключ. Дальше HTTP-трафик шифруется им, что даёт конфиденциальность и целостность.

### Как сервер понимает, что запрос пришёл от залогиненного пользователя?
По учётным данным в каждом запросе: cookie с идентификатором сессии, которую сервер хранит у себя, или токен (например, JWT) в заголовке Authorization, подпись которого сервер проверяет. Cookie с сессией ставят с флагами HttpOnly, Secure, SameSite.
