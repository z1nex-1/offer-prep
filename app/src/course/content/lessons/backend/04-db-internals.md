### Индексы

Без индекса поиск `WHERE email = '...'` читает всю таблицу — O(n). **Индекс** — дополнительная структура, отсортированная по значению столбца и хранящая ссылки на строки.

**B-дерево** (точнее, B+-дерево) — основной тип индекса в PostgreSQL и MySQL: сбалансированное дерево с большим ветвлением (сотни ключей в узле), листья связаны в список. Поиск — O(log n) с очень маленьким основанием: на миллиард строк хватает 3–4 чтений страниц. Поддерживает `=`, `<`, `>`, `BETWEEN`, `ORDER BY`, префиксный `LIKE 'abc%'`.

**Хеш-индекс** — только равенство, зато O(1).

**Цена индекса:**

- место на диске;
- замедление `INSERT`, `UPDATE`, `DELETE` — индекс нужно обновлять;
- при низкой селективности (столбец «пол», «статус» с парой значений) планировщик всё равно выберет полный проход.

### Когда индекс не используется

- функция или выражение над столбцом: `WHERE lower(email) = ...` (нужен индекс по выражению), `WHERE created_at::date = ...`;
- `LIKE '%abc'` — поиск по суффиксу;
- неявное приведение типов (число сравнивается со строкой);
- условие не по первому столбцу составного индекса;
- таблица маленькая или условие отбирает большую долю строк — полный проход дешевле.

### Составные и покрывающие индексы

Индекс по `(user_id, created_at)` отсортирован сначала по `user_id`, внутри — по `created_at`. Он помогает:

- `WHERE user_id = 5`;
- `WHERE user_id = 5 AND created_at > '2026-01-01'`;
- `WHERE user_id = 5 ORDER BY created_at`.

И **не** помогает `WHERE created_at > ...` без `user_id` — правило «левого префикса». Порядок столбцов выбирают по запросам: сначала столбцы с равенством, потом с диапазоном.

**Покрывающий индекс** содержит все столбцы, нужные запросу, — база отвечает только по индексу, не читая таблицу (Index Only Scan).

### EXPLAIN

`EXPLAIN ANALYZE SELECT ...` показывает план запроса: `Seq Scan` (полный проход), `Index Scan`, `Index Only Scan`, виды соединений (`Nested Loop`, `Hash Join`, `Merge Join`), оценки и фактическое число строк и время. Первый шаг при медленном запросе — посмотреть план.

### Транзакции и ACID

Транзакция — группа операций, которая выполняется как одно целое:

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;      -- или ROLLBACK при ошибке
```

- **Atomicity** — атомарность: либо все изменения, либо ни одного.
- **Consistency** — согласованность: после транзакции данные удовлетворяют ограничениям (ключи, `CHECK`, уникальность).
- **Isolation** — изоляция: параллельные транзакции не мешают друг другу (в пределах выбранного уровня).
- **Durability** — долговечность: после `COMMIT` данные переживут сбой (журнал предзаписи, WAL).

### Уровни изоляции и аномалии

| Аномалия | Что происходит |
|---|---|
| Грязное чтение | читаем незакоммиченные изменения другой транзакции |
| Неповторяющееся чтение | повторное чтение той же строки даёт другое значение |
| Фантомное чтение | повторный запрос по условию возвращает другой набор строк |
| Потерянное обновление | две транзакции читают значение и перезаписывают друг друга |
| Аномалия сериализации (write skew) | каждая транзакция по отдельности корректна, вместе — нарушают правило |

| Уровень | Грязное | Неповторяющееся | Фантомы |
|---|---|---|---|
| Read Uncommitted | возможно | возможно | возможно |
| Read Committed (по умолчанию в PostgreSQL) | нет | возможно | возможно |
| Repeatable Read (по умолчанию в MySQL InnoDB) | нет | нет | по стандарту возможно, в PostgreSQL и InnoDB в основном нет |
| Serializable | нет | нет | нет |

Чем выше изоляция, тем больше конфликтов и повторов транзакций. Потерянное обновление в Read Committed предотвращают `SELECT ... FOR UPDATE` (блокировка строки) или атомарным `UPDATE ... SET x = x - 1`.

### Блокировки и MVCC

- **Блокировки**: строки блокируются на запись; при чтении с `FOR UPDATE` — тоже. Две транзакции, ждущие друг друга, — **deadlock**; база обнаружит его и откатит одну.
- **MVCC** (многоверсионность, PostgreSQL, InnoDB): при изменении создаётся новая версия строки, а читатели видят снимок данных на момент начала запроса или транзакции. Читатели не блокируют писателей и наоборот. Старые версии потом удаляет очистка (VACUUM в PostgreSQL).

### Нормализация

Нормализация убирает дублирование: каждый факт хранится в одном месте.

- **1НФ** — атомарные значения, нет списков в ячейках;
- **2НФ** — неключевые столбцы зависят от всего составного ключа;
- **3НФ** — неключевые столбцы не зависят друг от друга (город не хранится вместе с его населением в таблице заказов).

**Денормализация** — осознанное дублирование ради скорости чтения (счётчик комментариев в таблице постов). Цена — нужно поддерживать согласованность копий.

### Масштабирование

- **Репликация**: копии базы на других серверах. Мастер принимает запись, реплики — чтение. Асинхронная репликация быстрее, но реплика может отставать (прочитали старые данные сразу после записи); синхронная надёжнее, но медленнее запись.
- **Шардирование**: данные делятся между серверами по ключу (`user_id % N`, диапазоны, консистентное хеширование). Масштабирует запись и объём, но усложняет запросы через шарды и транзакции между ними.
- **Партиционирование**: деление таблицы на части внутри одного сервера (по дате) — быстрее удалять старое и искать в свежем.

### NoSQL и CAP

- **Ключ-значение** (Redis, Memcached) — кэши, сессии, счётчики, очереди; очень быстро, данные часто в памяти.
- **Документные** (MongoDB) — JSON-документы с гибкой схемой.
- **Колоночные** (ClickHouse — разработан в Яндексе) — аналитика по огромным объёмам: читаются только нужные столбцы, хорошее сжатие.
- **Широкие колонки** (Cassandra), **графовые** (Neo4j).

**Теорема CAP**: при сетевом разделении (P) распределённая система выбирает между согласованностью (C — все видят последнюю запись) и доступностью (A — каждый запрос получает ответ). На практике говорят о компромиссах: согласованность «в конечном счёте» (eventual consistency) против строгой.

### Типичные ошибки

- «Индекс ускоряет всё» — он замедляет запись и не помогает при низкой селективности.
- Порядок столбцов составного индекса выбран без учёта запросов.
- Функция над индексированным столбцом в `WHERE`.
- Уверенность, что транзакция сама защищает от потерянного обновления на любом уровне изоляции.
- Чтение с асинхронной реплики сразу после записи в мастер.

### Как спрашивают на Яндексе

Индексы и транзакции — самые частые вопросы по базам данных на бэкенд-собеседованиях: «как устроен индекс», «почему запрос не использует индекс», «что такое ACID и уровни изоляции». На странице стажировки знание баз данных и SQL, а также опыт распределённых вычислений перечислены среди преимуществ. ClickHouse и YDB — базы данных, которые разрабатывает Яндекс, — хороший повод показать интерес к компании.

## Вопросы на собеседовании

### Как работает индекс и почему он ускоряет поиск?
Индекс — отдельная отсортированная структура (обычно B+-дерево) из значений столбца и ссылок на строки. Поиск идёт от корня к листу за O(log n) чтений страниц вместо полного прохода; листья связаны, поэтому диапазоны и сортировка тоже быстрые. Цена — место и замедление записи. Индекс не помогает при функции над столбцом, суффиксном LIKE, условии не по левому префиксу составного индекса и низкой селективности.

### Что такое ACID?
Атомарность — транзакция выполняется целиком или никак. Согласованность — после неё соблюдены все ограничения. Изоляция — параллельные транзакции не видят промежуточных состояний друг друга в пределах уровня изоляции. Долговечность — после коммита данные сохранятся при сбое благодаря журналу.

### Какие есть уровни изоляции и какие аномалии они допускают?
Read Uncommitted допускает грязное чтение. Read Committed — нет, но допускает неповторяющееся чтение и фантомы. Repeatable Read запрещает неповторяющееся чтение (фантомы по стандарту возможны, в PostgreSQL на этом уровне их нет). Serializable даёт результат, эквивалентный последовательному выполнению. Выше уровень — больше конфликтов и откатов.

### Как бы вы ускорили медленный запрос?
Посмотреть план через EXPLAIN ANALYZE: полный проход там, где ожидался индекс, неверные оценки числа строк, дорогой вид соединения. Затем — индекс под условия и сортировку (с правильным порядком столбцов, возможно покрывающий), переписать условие без функций над столбцом, обновить статистику, ограничить выборку, кэшировать результат или денормализовать, если запрос критичен.
