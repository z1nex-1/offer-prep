### Задача

Нужна структура, где по ключу можно за O(1) найти, добавить и удалить значение. Массив даёт O(1) доступ, но только по целому индексу от 0 до размера. Хеш-таблица превращает **любой ключ в индекс массива**.

### Хеш-функция

Хеш-функция `hash(key)` превращает ключ в целое число. Требования:

1. **Детерминированность:** один и тот же ключ — всегда один и тот же хеш (за время работы программы).
2. **Согласованность с равенством:** если `a == b`, то `hash(a) == hash(b)`. Обратное не обязано выполняться.
3. **Равномерность:** разные ключи должны по возможности давать разные, «разбросанные» хеши.

Индекс корзины получается из хеша: `index = hash(key) % capacity` (в CPython — через битовую маску, потому что ёмкость — степень двойки).

```python
print(hash(42))        # для небольших int хеш равен самому числу
print(hash("abc"))     # у строк хеш меняется между запусками интерпретатора
```

Хеш строк в Python **рандомизирован** при каждом запуске (защита от атак, когда злоумышленник подбирает ключи с одинаковым хешем и замедляет сервер). Поэтому порядок элементов `set` строк может отличаться между запусками.

### Коллизии

Ключей бесконечно много, корзин — конечное число, поэтому разные ключи неизбежно попадают в одну корзину. Это **коллизия**. Два основных способа их разрешать:

**Метод цепочек.** В каждой корзине — список пар (ключ, значение). Поиск: вычислить корзину, пройти её список, сравнивая ключи через `==`. Так устроены `HashMap` в Java и `unordered_map` в C++.

**Открытая адресация.** Все пары лежат прямо в массиве. Если корзина занята другим ключом, пробуем следующую по некоторому правилу (линейное пробирование `i+1, i+2, …`, квадратичное, или псевдослучайная последовательность). Поиск идёт по той же последовательности до нужного ключа или пустой ячейки. Так устроены `dict` и `set` в CPython — они используют псевдослучайное пробирование, зависящее от старших битов хеша.

Удаление при открытой адресации нельзя делать просто очисткой ячейки: это разорвёт цепочку пробирования для других ключей. Вместо этого ставят метку «удалено» (tombstone).

### Коэффициент заполнения и расширение

**Коэффициент заполнения** — доля занятых корзин. Чем он выше, тем больше коллизий и длиннее поиск. Поэтому при достижении порога (у `dict` в CPython — около 2/3) таблица **расширяется**: выделяется массив большего размера, и все элементы перераспределяются по новым корзинам (rehash) — это O(n).

Расширения происходят при геометрически растущих размерах, поэтому, как и у `list.append`, вставка стоит **O(1) амортизированно**.

### Почему O(1) — «в среднем»

При хорошей хеш-функции и ограниченном коэффициенте заполнения в каждой корзине в среднем константное число элементов — операции O(1). Но в **худшем** случае все ключи попадают в одну корзину, и поиск вырождается в линейный — O(n).

Когда это бывает на практике:

- плохая пользовательская хеш-функция (например, `__hash__`, возвращающий константу);
- специально подобранные ключи (атака на хеш-таблицу — отсюда рандомизация хеша строк).

В Java `HashMap` при длинной цепочке превращает её в сбалансированное дерево, и худший случай становится O(log n).

### Порядок в словаре Python

С версии 3.6 `dict` хранит записи в **компактном массиве в порядке вставки**, а хеш-таблица содержит только индексы в этот массив. Это экономит память и делает обход быстрым. С 3.7 сохранение порядка вставки — часть спецификации языка. У `set` такой гарантии нет.

### Требования к ключам в Python

Ключ должен быть хешируемым: иметь `__hash__` и `__eq__`, согласованные друг с другом, и хеш не должен меняться. Поэтому:

- `list`, `dict`, `set` — нехешируемы (изменяемы);
- `tuple` хешируем, если хешируемы все элементы;
- пользовательский класс по умолчанию хешируется по `id` объекта; если вы переопределили `__eq__`, Python обнуляет `__hash__`, и объект становится нехешируемым, пока вы не определите `__hash__` сами.

Если изменить объект, лежащий в множестве, так, что его хеш поменяется, он «потеряется»: `x in s` будет искать в другой корзине.

### Хеш-таблица против сбалансированного дерева

| | Хеш-таблица (`dict`) | Сбалансированное дерево (`std::map`, `TreeMap`) |
|---|---|---|
| Поиск, вставка, удаление | O(1) в среднем | O(log n) гарантированно |
| Порядок ключей | нет (в Python — порядок вставки) | отсортирован |
| «Следующий больший ключ», диапазоны | нет | O(log n) |
| Требование к ключу | хешируемость | сравнимость |

В стандартной библиотеке Python нет сбалансированного дерева. Если нужны упорядоченные операции, используют отсортированный список с `bisect` (вставка O(n)) или кучу, если нужен только минимум.

### Типичные ошибки

- Называть O(1) без оговорки. Правильно — «O(1) в среднем», худший случай O(n) при плохом хеше или специально подобранных ключах.
- Класть в словарь изменяемые объекты или менять ключ после вставки.
- Переопределить `__eq__` в классе и удивиться, что объекты больше нельзя положить в `set`: нужен ещё `__hash__`.
- Полагаться на порядок `set`: он не определён, в отличие от порядка вставки в `dict`.
- Использовать словарь там, где ключи — маленькие целые: список `cnt = [0] * size` проще и быстрее.

- [x] Чтобы нельзя было заранее подобрать много ключей с одинаковым хешем и замедлить сервис до O(n) на операцию

- [ ] Из-за Unicode
> Это защита от атак отказа в обслуживании (hash flooding) на веб-серверы, разбирающие параметры запросов в словари.

## Вопросы на собеседовании

### Как устроена хеш-таблица?
Массив корзин. Ключ хешируется, по хешу вычисляется номер корзины. Коллизии — когда разные ключи попали в одну корзину — решаются цепочками (список в корзине) или открытой адресацией (поиск другой свободной ячейки по правилу пробирования). Когда коэффициент заполнения превышает порог, массив увеличивается и все элементы перераспределяются. Операции — O(1) в среднем, O(n) в худшем случае.

### Чем dict отличается от TreeMap или std::map?
`dict` — хеш-таблица: O(1) в среднем, ключи должны быть хешируемыми, порядок — порядок вставки, диапазонных запросов нет. TreeMap/std::map — сбалансированное дерево поиска: O(log n) гарантированно, ключи должны сравниваться, хранятся отсортированными, есть «следующий больший» и выборка по диапазону.

### Что будет, если изменить объект, который лежит в множестве?
Если изменение влияет на хеш, объект останется в старой корзине, а поиск будет смотреть в новой — `x in s` вернёт `False`, а удалить его обычным способом не получится. Поэтому ключи должны быть неизменяемыми, а встроенные изменяемые коллекции сделаны нехешируемыми.
