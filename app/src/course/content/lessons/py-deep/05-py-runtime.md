### Как выполняется программа

CPython — основная реализация Python — компилирует исходный код в **байт-код** и выполняет его в виртуальной машине (цикл интерпретатора). Посмотреть байт-код: `import dis; dis.dis(func)`. Кэш байт-кода хранится в `__pycache__/*.pyc`.

Другие реализации: PyPy (JIT-компиляция, часто в разы быстрее на циклах), Jython, IronPython. Когда говорят «Python», обычно имеют в виду CPython — и всё, что ниже о памяти и GIL, относится к нему.

### Управление памятью

**Подсчёт ссылок.** У каждого объекта есть счётчик ссылок. Присваивание, добавление в список, передача в функцию увеличивают его; выход из области видимости, `del`, перепривязка имени — уменьшают. Когда счётчик падает до нуля, объект удаляется **сразу**.

```python
import sys
a = []
b = a
print(sys.getrefcount(a))   # обычно 3: a, b и временная ссылка аргумента (точное число зависит от версии)
```

**Сборщик циклических ссылок.** Подсчёт ссылок не справляется с циклами: `a.next = b; b.next = a` — после удаления внешних имён счётчики остаются по единице. Для этого есть модуль `gc`: он периодически ищет группы объектов, недостижимых извне, и удаляет их. Объекты разбиты на три поколения: новые проверяются часто, выжившие — реже (гипотеза «большинство объектов умирает молодыми»).

Следствия:

- память от большинства объектов освобождается предсказуемо и сразу;
- циклы освобождаются позже, при запуске `gc`;
- `weakref` — слабые ссылки, не увеличивающие счётчик (кэши, обратные ссылки на родителя);
- аллокатор CPython держит пулы мелких объектов и не всегда сразу возвращает память операционной системе.

### GIL

**Global Interpreter Lock** — глобальная блокировка в CPython: в каждый момент байт-код Python выполняет **только один поток** процесса. Потоки по очереди захватывают GIL и переключаются (по умолчанию примерно раз в 5 мс или при блокирующем вводе-выводе).

Зачем он: подсчёт ссылок и внутренние структуры интерпретатора не потокобезопасны; одна блокировка проще и быстрее для однопоточного кода, чем тонкие блокировки на каждом объекте, и упрощает C-расширения.

Следствия:

- **CPU-bound** задачи (вычисления на чистом Python) потоки **не ускоряют** — выполняется один поток за раз, а переключения добавляют накладные расходы;
- **I/O-bound** задачи (сеть, диск, база) потоки ускоряют: во время ожидания ввода-вывода GIL освобождается, и работают другие потоки;
- C-расширения (numpy, хеширование, сжатие) могут отпускать GIL во время тяжёлых вычислений.

С Python 3.13 есть экспериментальная сборка без GIL (free-threaded, PEP 703), но по умолчанию GIL на месте — на собеседовании стоит сказать и об этом.

### Потоки, процессы, asyncio — что выбрать

| | `threading` | `multiprocessing` / `ProcessPoolExecutor` | `asyncio` |
|---|---|---|---|
| Что это | несколько потоков в одном процессе | несколько процессов со своими интерпретаторами | одна нить, кооперативная многозадачность |
| GIL | общий | у каждого процесса свой | один поток — не мешает |
| Для чего | I/O-bound, простой код, блокирующие библиотеки | CPU-bound: вычисления на всех ядрах | тысячи одновременных сетевых соединений |
| Память | общая | раздельная, данные передаются сериализацией (pickle) | общая |
| Стоимость | поток ~ мегабайты стека | процесс — дорого создавать | корутина — килобайты |
| Опасности | гонки данных, deadlock | накладные расходы на передачу данных | блокирующий вызов останавливает всё |

Удобный высокоуровневый интерфейс для первых двух — `concurrent.futures`:

```python
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

with ThreadPoolExecutor(max_workers=16) as pool:        # 16 HTTP-запросов параллельно
    pages = list(pool.map(download, urls))

with ProcessPoolExecutor() as pool:                     # вычисления на всех ядрах
    results = list(pool.map(heavy_compute, chunks))
```

### asyncio и async/await

Асинхронный код выполняется в **одном потоке**. Функция `async def` — корутина; `await` отдаёт управление **циклу событий** (event loop), пока идёт ожидание (ответ сети, таймер), и цикл в это время выполняет другие корутины.

```python
import asyncio

async def fetch(i):
    await asyncio.sleep(1)         # имитация сетевого запроса
    return i * 10

async def main():
    results = await asyncio.gather(*(fetch(i) for i in range(100)))
    print(len(results))            # 100 «запросов» примерно за 1 секунду, а не за 100

asyncio.run(main())
```

Главное правило: внутри корутины **нельзя** вызывать блокирующие функции (`time.sleep`, `requests.get`, долгие вычисления) — они остановят весь цикл событий, и все остальные корутины будут ждать. Нужны асинхронные библиотеки (`aiohttp`, `httpx`, `asyncpg`) или вынос блокирующего кода в поток: `await asyncio.to_thread(func, ...)`.

На asyncio построены современные веб-фреймворки: FastAPI, aiohttp, Starlette.

### Гонки и синхронизация

Даже с GIL потоки могут испортить общие данные: `counter += 1` — это несколько операций байт-кода (прочитать, сложить, записать), и переключение потока между ними теряет обновления.

```python
import threading

counter = 0
lock = threading.Lock()

def work():
    global counter
    for _ in range(100_000):
        with lock:                 # без блокировки итог может быть меньше ожидаемого
            counter += 1
```

Инструменты: `Lock`, `RLock`, `Semaphore`, `Event`, `Condition`, потокобезопасная `queue.Queue` для схемы «производитель — потребитель». **Deadlock** возникает, когда два потока ждут блокировки друг друга; защита — всегда брать блокировки в одном порядке и держать их как можно меньше.

### Типичные ошибки

- Ожидание, что потоки ускорят вычисления на чистом Python.
- Блокирующий вызов внутри `async def`.
- Общий изменяемый объект в потоках без блокировки.
- Передача в `ProcessPoolExecutor` огромных объектов — их сериализация съедает весь выигрыш.
- Уверенность, что память освобождается только сборщиком мусора: основную работу делает подсчёт ссылок.

## Вопросы на собеседовании

### Что такое GIL и как он влияет на многопоточность?
Global Interpreter Lock — блокировка в CPython, из-за которой байт-код Python в каждый момент выполняет один поток процесса. Нужна, потому что подсчёт ссылок и внутренности интерпретатора не потокобезопасны. Потоки не ускоряют CPU-bound код на чистом Python, но ускоряют I/O-bound: во время ввода-вывода GIL отпускается. Для вычислений на нескольких ядрах — процессы или C-расширения. В 3.13 появилась экспериментальная сборка без GIL.

### Чем отличаются потоки, процессы и asyncio? Когда что использовать?
Потоки — в одном процессе с общей памятью, ограничены GIL, подходят для блокирующего ввода-вывода. Процессы — отдельные интерпретаторы со своим GIL и памятью, подходят для вычислений, но данные между ними сериализуются. Asyncio — один поток и цикл событий с кооперативными корутинами: тысячи одновременных сетевых операций с минимальными накладными расходами, но любой блокирующий вызов останавливает всё.

### Как в Python управляется память?
Основной механизм — подсчёт ссылок: объект удаляется сразу, когда на него не остаётся ссылок. Циклические ссылки ищет сборщик мусора по поколениям (модуль `gc`). Мелкие объекты выделяются из пулов собственного аллокатора CPython. Слабые ссылки (`weakref`) позволяют ссылаться на объект, не продлевая его жизнь.

### Что такое event loop?
Цикл, который держит очередь готовых к выполнению корутин и колбэков и ждёт событий ввода-вывода (через epoll/kqueue). Корутина выполняется до `await` на неготовой операции, затем цикл переключается на другую; когда операция завершается, корутина возобновляется. Всё происходит в одном потоке, поэтому нет гонок между `await`, но блокирующий код останавливает весь цикл.
