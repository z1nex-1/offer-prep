### Исключения: как они работают

Ошибка во время выполнения создаёт объект-исключение и **раскручивает стек**: интерпретатор выходит из функций, пока не найдёт подходящий `except`. Не нашёл — программа падает с трейсбеком.

```python
def parse_age(s):
    try:
        age = int(s)
    except ValueError:
        raise ValueError(f"возраст должен быть числом, получено {s!r}") from None
    else:
        if age < 0:
            raise ValueError("возраст не может быть отрицательным")
        return age
    finally:
        print("проверка завершена")      # выполнится в любом случае
```

- `except` ловит исключения указанного типа **и его наследников**. Порядок важен: сначала частные, потом общие.
- `else` — выполняется, если в `try` исключения не было. Туда кладут код, ошибки которого вы **не** хотите ловить этим `except`.
- `finally` — выполняется всегда: при успехе, при исключении, при `return` внутри `try`. Место для освобождения ресурсов (или используйте `with`).
- `raise` без аргументов внутри `except` пробрасывает текущее исключение дальше.

### Иерархия

```
BaseException
 ├── SystemExit, KeyboardInterrupt, GeneratorExit
 └── Exception
      ├── ArithmeticError → ZeroDivisionError, OverflowError
      ├── LookupError → IndexError, KeyError
      ├── ValueError, TypeError, AttributeError, NameError
      ├── OSError → FileNotFoundError, ConnectionError, TimeoutError …
      ├── RuntimeError → RecursionError, NotImplementedError
      └── StopIteration …
```

`except Exception` не ловит `KeyboardInterrupt` и `SystemExit` — и правильно: Ctrl+C и `sys.exit()` должны работать. Голый `except:` ловит всё, включая их, — плохая практика.

### raise from и цепочки

`raise NewError(...) from err` сохраняет исходное исключение в `__cause__` — в трейсбеке будет видна причина. `from None` скрывает исходное исключение, когда оно только шумит. Без `from` Python сам сохранит контекст в `__context__` («During handling of the above exception, another exception occurred»).

### Свои исключения

```python
class PaymentError(Exception):
    """Базовая ошибка платёжного модуля."""

class InsufficientFunds(PaymentError):
    def __init__(self, need, have):
        super().__init__(f"не хватает {need - have}")
        self.need, self.have = need, have
```

Иерархия своих исключений позволяет вызывающему коду ловить и конкретную ошибку, и «любую ошибку модуля».

### EAFP и LBYL

- **LBYL** («look before you leap»): проверить, потом делать — `if key in d: v = d[key]`.
- **EAFP** («easier to ask forgiveness than permission»): сделать и обработать исключение — `try: v = d[key] except KeyError: ...`.

В Python принят EAFP: проверка и действие — одна операция без окна для гонки (файл могли удалить между `os.path.exists` и `open`). Но исключения дороже обычной проверки, если срабатывают часто; для словаря чаще всего проще `d.get(key, default)`.

### Аннотации типов

```python
from typing import Optional

def find_user(users: dict[int, str], uid: int) -> Optional[str]:
    return users.get(uid)

def total(prices: list[float], discount: float = 0.0) -> float:
    return sum(prices) * (1 - discount)
```

- Аннотации **не проверяются** во время выполнения — это подсказки для людей, IDE и статических анализаторов (`mypy`, `pyright`).
- `int | None` (с 3.10) — то же, что `Optional[int]`; `list[int]`, `dict[str, int]` — встроенные дженерики с 3.9.
- `TypedDict`, `Protocol`, `Callable`, `Literal`, `TypeVar` — для сложных случаев.
- FastAPI и Pydantic используют аннотации по-настоящему: валидируют и преобразуют входные данные по типам.

### Модули и импорт

- Модуль — файл `.py`, пакет — каталог с модулями (обычно с `__init__.py`).
- `import x` при первом выполнении ищет модуль по `sys.path`, **выполняет его код** один раз и кладёт в кэш `sys.modules`. Повторные импорты берут объект из кэша.
- Циклические импорты (a импортирует b, b импортирует a) приводят к `ImportError` или частично инициализированным модулям; лечится переносом общего кода в третий модуль или импортом внутри функции.

`if __name__ == "__main__":` — код внутри выполняется, только если файл запущен как программа, а не импортирован. Так один файл может быть и модулем, и скриптом.

### Окружение и зависимости

Каждый проект держат в своём **виртуальном окружении** (`python -m venv .venv`), чтобы версии библиотек разных проектов не конфликтовали. Зависимости фиксируют в `requirements.txt` или `pyproject.toml` (менеджеры poetry, uv). На собеседовании бэкенд-стажёра это спрашивают как «как вы запускаете свой проект».

### Типичные ошибки

- Голый `except:` или `except Exception: pass` — ошибки молча проглатываются.
- Слишком широкий `try`: в него попадает код, чьи ошибки не должны ловиться этим обработчиком.
- `return` внутри `finally` — подавляет исключение из `try`.
- Ожидание, что аннотации типов что-то проверяют во время выполнения.
- Тяжёлый код на верхнем уровне модуля — выполняется при каждом импорте.

### Как спрашивают на Яндексе

Вопросы о `try/except/else/finally`, иерархии исключений и `__name__ == "__main__"` — часть проверки знания языка на технических секциях. В задачах на код исключения появляются, когда вы реализуете класс или разбираете ввод: интервьюер может спросить, что будет при некорректных данных. Аккуратная обработка ошибок и понятные имена — то, что Яндекс называет читаемым кодом.

## Самопроверка

### Что выведет код?
```python
def f():
    try:
        return "try"
    finally:
        print("finally")

print(f())
```
- [ ] `try`
- [x] `finally` и затем `try` (на отдельных строках)
- [ ] `try` и затем `finally`
- [ ] Ошибку
> `finally` выполняется перед фактическим выходом из функции, даже при `return` в `try`.

### Что выведет код?
```python
try:
    d = {}
    d["x"]
except LookupError:
    print("lookup")
except KeyError:
    print("key")
```
- [x] `lookup`
- [ ] `key`
- [ ] `lookup` и `key`
- [ ] Ошибку
> `KeyError` — наследник `LookupError`, срабатывает первый подходящий обработчик.

### Когда выполняется блок `else` у try?
- [ ] Всегда
- [x] Если в блоке try не было исключения
- [ ] Если исключение было поймано
- [ ] Перед finally, только при исключении
> В `else` кладут код, чьи ошибки не должны ловиться этими `except`.

### Проверяются ли аннотации типов при выполнении?
- [ ] Да, всегда
- [x] Нет, это подсказки для людей и анализаторов вроде mypy
- [ ] Только в строгом режиме
- [ ] Только для аргументов функций
> Проверку во время выполнения делают отдельные библиотеки, например Pydantic.

### Что делает `if __name__ == "__main__":`?
- [ ] Ускоряет запуск
- [x] Выполняет код только при запуске файла как программы, а не при импорте
- [ ] Объявляет главную функцию
- [ ] Запрещает импорт модуля
> При импорте `__name__` равно имени модуля.

### Почему голый `except:` — плохая практика?
- [ ] Он медленный
- [x] Он ловит всё, включая KeyboardInterrupt и SystemExit, и скрывает ошибки

- [ ] Он запрещён синтаксисом
> Ловите конкретные исключения, в крайнем случае `Exception`, и логируйте их.

## Вопросы на собеседовании

### Как работает try/except/else/finally?
Выполняется `try`; если возникло исключение, ищется первый `except` с подходящим типом (с учётом наследования) и выполняется он; если исключения не было — выполняется `else`. `finally` выполняется в любом случае — после успеха, после обработки, при непойманном исключении и даже при `return` внутри `try` — поэтому там освобождают ресурсы.

### Что такое EAFP и почему в Python его предпочитают?
«Проще попросить прощения, чем разрешения»: выполнить операцию и обработать исключение вместо предварительной проверки. Нет окна между проверкой и действием (гонки с файлами, соединениями), код короче. Но если исключение ожидается часто, проверка дешевле — например, `dict.get` вместо `try/except KeyError` в горячем цикле.

### Что происходит при import?
Интерпретатор ищет модуль в `sys.modules`; если его нет — ищет файл по `sys.path`, создаёт объект модуля, выполняет его код сверху вниз и кэширует в `sys.modules`. Повторный импорт возвращает кэшированный объект, код не выполняется снова. Поэтому побочные эффекты на верхнем уровне модуля происходят один раз при первом импорте.
