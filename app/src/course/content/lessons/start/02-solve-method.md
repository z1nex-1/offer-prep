### Откуда этот метод

У Яндекса есть [официальная статья об алгоритмических секциях](https://yandex.ru/jobs/interview/algorithms) с «пошаговой инструкцией от авторов наших задач». Метод оттуда подходит и для секции, и для контеста: на контесте нет собеседника, но ошибки те же. Ниже — эти шаги, разобранные на задачах, которые Яндекс сам приводит в пример.

Шаги:

1. Понять условие и придумать **тестовые примеры** — до кода.
2. Сформулировать **алгоритм словами**: какие переменные, какие структуры данных.
3. **Оценить сложность** и сравнить с ограничениями.
4. Написать **короткий код** без дублирования и лишних частных случаев.
5. **Проверить код вручную** на своих примерах, отслеживая значения переменных.

### Шаг 1. Примеры до кода

Задача из статьи: дан массив из нулей и единиц, найти длину самой длинной серии единиц подряд.

Прежде чем думать о решении, выпишите примеры с ответами. В статье приведён такой набор:

| Вход | Ответ | Что проверяет |
|---|---|---|
| `[1, 0, 1, 1, 0]` | 2 | обычный случай |
| `[1, 1, 1]` | 3 | серия до самого конца массива |
| `[0, 0, 0]` | 0 | единиц нет |
| `[]` | 0 | пустой вход |
| `[0, 1, 1, 1, 0, 1]` | 3 | лучшая серия не последняя |

Примеры решают три задачи сразу: вы убеждаетесь, что поняли условие, находите краевые случаи и показываете собеседующему методичный подход. На секции проговорите примеры вслух и спросите: «Правильно ли я понимаю, что для пустого массива ответ 0?» — это нормальный уточняющий вопрос, а не слабость.

Какие примеры придумывать почти всегда:

- самый маленький вход (пустой, один элемент);
- «всё одинаковое» и «всё разное»;
- ответ находится в самом начале и в самом конце;
- случай, где простое жадное рассуждение ошибается (подробнее — в модуле про жадные алгоритмы).

На контесте примеры из условия уже есть, но их мало и они простые. Прогоните их **в голове** до того, как писать код: так проще заметить, что вы неправильно поняли формат. Дежурный администратор отбора в бэкенд [советует](https://education.yandex.ru/journal/otbor-na-stazirovky-backend-yandexa) именно это: «попробуйте в уме провести условия через тесты».

### Шаг 2. Алгоритм словами

Опишите решение одной-двумя фразами, не глядя в код:

> Иду по массиву слева направо и держу два числа: длину текущей серии единиц и лучшую длину. Встретил единицу — текущая серия растёт на 1, иначе обнуляется. После каждого шага обновляю лучшую.

Если фраза не складывается, код тоже не сложится. В статье это названо самой популярной ошибкой: «писать код, до того как продумаешь решение до конца. Лучше потратить дополнительные пять минут на размышления, чем двадцать — на написание неэффективного алгоритма».

На секции есть и практическая причина: собеседующий не пустит вас писать код, пока вы не предложили эффективное решение. Поэтому сначала обсуждаете идею, потом пишете.

### Шаг 3. Сложность

Для каждой идеи сразу называйте время и память. У серии единиц — один проход: время O(n), память O(1).

На контесте сложность сравнивают с ограничениями. Грубое правило для Python: за секунду выполняется порядка 10⁷ простых операций. Значит, при n до 10⁵ решение O(n²) — это 10¹⁰ операций, и оно не успеет; O(n log n) успеет с запасом. Подробно — в модуле «Сложность алгоритмов».

На секции спросят: «Можно ли быстрее? А с меньшей памятью?» Если вы уже знаете ответ («быстрее O(n) нельзя: каждый элемент нужно хотя бы прочитать»), скажите его сами.

### Шаг 4. Короткий код без лишних частных случаев

Хорошие практики из статьи: код без дублирования, **минимальная обработка специальных случаев**, понятная логика. Сравните два решения, которые приводит Яндекс.

Слишком сложно:

```python
def max_ones_sequence(arr):
    if not arr:
        return 0
    current_count = 1 if arr[0] == 1 else 0
    max_count = current_count
    for i in range(1, len(arr)):
        if arr[i] == 1:
            current_count += 1
        else:
            current_count = 0
        max_count = max(max_count, current_count)
    return max_count
```

Проще:

```python
def max_ones_sequence(arr):
    current_count = 0
    max_count = 0
    for num in arr:
        if num == 1:
            current_count += 1
        else:
            current_count = 0
        max_count = max(max_count, current_count)
    return max_count
```

Второй вариант сам обрабатывает пустой массив: цикл не выполнится ни разу, вернётся 0. Отдельная ветка для первого элемента не нужна, потому что правильно выбраны начальные значения. Отсюда общий приём: **прежде чем писать `if` для краевого случая, проверьте, не обработает ли его основной алгоритм сам**. Каждая лишняя ветка — ещё одно место для ошибки и ещё одна вещь, которую нужно проверить.

Это не значит «никогда не проверять краевые случаи». Это значит — проверять их на шаге 5 и добавлять код только тогда, когда основной алгоритм действительно ломается.

### Шаг 5. Проверка вручную

Код на секции не запускают, поэтому проверять его нужно «на бумаге»: взять пример из шага 1 и выписать значения переменных после каждой итерации. Для `[1, 0, 1, 1, 0]`:

| Шаг | `num` | `current_count` | `max_count` |
|---|---|---|---|
| старт | — | 0 | 0 |
| 1 | 1 | 1 | 1 |
| 2 | 0 | 0 | 1 |
| 3 | 1 | 1 | 1 |
| 4 | 1 | 2 | 2 |
| 5 | 0 | 0 | 2 |

Ответ 2 — совпадает. Затем пройдите быстро пустой массив и `[1, 1, 1]`: серия, которая заканчивается в последнем элементе, — классическое место ошибки, когда максимум обновляют только в ветке `else`.

Если вы нашли ошибку сами — это плюс, а не минус. В статье прямо сказано: «Если вы допустили ошибку, но сами её обнаружили и исправили — собеседующий оценит вашу внимательность».

### Второй пример: анаграммы и три неверных решения

Задача из той же статьи: даны две строки, проверить, что они различаются только порядком букв.

Шаг 1 — примеры: `"listen"` и `"silent"` → да; `"aab"` и `"abb"` → **нет** (буквы одни и те же, а количество разное); `"ab"` и `"abc"` → нет; две пустые строки → да.

Пример `"aab"`/`"abb"` сразу отсекает первое неверное решение из статьи:

```python
# НЕВЕРНО: множества не учитывают, сколько раз встречается буква
def are_anagrams(a, b):
    return set(a) == set(b)
```

Второе неверное решение — проверить, что каждая буква `a` есть в `b`. Оно нарушает симметрию: для `"ab"` и `"abc"` вернёт `True`, хотя в `b` лишняя буква.

Шаг 2 — словами: посчитать, сколько раз встречается каждая буква в каждой строке, и сравнить эти подсчёты.

Шаг 3 — время O(n + m), память O(размер алфавита).

Шаг 4 — код:

```python
from collections import Counter


def are_anagrams(a, b):
    return Counter(a) == Counter(b)
```

В статье приведён вариант с двумя `defaultdict(int)` — он длиннее, но показывает, что вы понимаете, что внутри `Counter`. На секции можно написать короткий вариант и сказать, как он устроен. Отсортировать обе строки и сравнить — тоже верное решение, но за O(n log n).

Шаг 5 — прогнать `"aab"`/`"abb"`: `Counter({'a': 2, 'b': 1})` ≠ `Counter({'a': 1, 'b': 2})` → `False`. Верно.

### Как метод выглядит на контесте

На контесте тот же порядок, только собеседник — проверяющая система:

1. Прочитать условие и ограничения, прогнать примеры в голове.
2. По ограничениям понять, какая сложность нужна (n ≤ 10⁵ — не хуже O(n log n)).
3. Сформулировать идею словами. Если идея не находится за 15–20 минут — перейти к другой задаче и вернуться позже.
4. Написать код, прогнать примеры из условия и свои краевые случаи.
5. Получили WA — не отправлять наугад исправления, а искать тест, на котором решение ошибается: маленькие краевые случаи или сравнение с медленным переборным решением на случайных тестах. Как это сделать — в модуле «Python для контеста».

### Типичные ошибки

- **Начать с кода.** Самая частая ошибка по словам авторов задач. Через десять минут выясняется, что идея не работает, а переписывать жалко.
- **Проверять только пример из условия.** Он почти всегда «удобный»: без пустого входа, без повторов, с ответом в середине.
- **Обкладывать решение `if`-ами.** Три отдельные проверки на краевые случаи обычно означают, что неудачно выбраны начальные значения или границы цикла.
- **Молчать.** На секции оценивают не только результат, но и ход рассуждений. Проговаривайте, что делаете и почему.
- **Искать сложное решение.** Задачи рассчитаны на полчаса; если код разрастается до сотни строк, скорее всего, вы пошли не туда.

## Вопросы на собеседовании

### Как вы проверяете код, если его нельзя запустить?
Беру один-два примера из тех, что придумал в начале, и выполняю код построчно, записывая значения переменных после каждой итерации. Отдельно прохожу краевые случаи: пустой вход, один элемент, ответ в самом конце. Проверяю границы циклов (`range(n)` или `range(n + 1)`), начальные значения и что возвращается в конце.

### Зачем проговаривать решение до того, как писать код?
Чтобы собеседующий успел остановить, если идея неэффективна или неверна: переписывать код дороже, чем идею. Кроме того, оценивают ход рассуждений, а не только результат. Формула: «Идея такая-то, сложность такая-то, начинаю писать?»

### Когда стоит отдельно обрабатывать краевой случай?
Когда основной алгоритм на нём действительно ломается — например, деление на длину пустого списка или обращение к `a[0]`. Сначала стоит попробовать выбрать начальные значения и границы так, чтобы случай обработался сам: код получается короче, а проверять нужно меньше веток.
