### Почему это отдельный навык

На контесте тесты скрыты: вы видите только вердикт и номер первого непройденного теста. Отладчика нет, а время идёт. Поэтому ошибку ищут не «вглядываясь в код», а методично: сначала гипотеза по вердикту, потом тест, который её подтверждает. Краткий порядок действий есть в уроке «Контест на Python: ввод, скорость, вердикты, стратегия» — здесь он разобран подробно, с готовым кодом стресс-теста.

### Шаг 1. Вердикт подсказывает, где искать

| Вердикт | Что проверить первым |
|---|---|
| WA на тесте 1 | пример из условия: формат ввода и вывода, лишний текст, порядок чисел |
| WA на дальнем тесте | краевые случаи и ошибка в идее — нужен стресс-тест |
| TL | асимптотика по ограничениям, затем медленный ввод-вывод и лишняя работа в цикле |
| RE | `IndexError` на краевом входе, глубокая рекурсия, деление на ноль, ввод не того формата |
| ML | лишние копии списков, матрица n × n при n = 10⁵ |

### Шаг 2. Краевые случаи по типам входа

Прежде чем писать стресс-тест, прогоните решение руками на тестах из этого списка — половина ошибок находится здесь.

- **Числа**: 0, 1, отрицательные, максимальные по ограничениям, все одинаковые.
- **Массив**: n = 1 (и n = 0, если разрешено), все элементы равны, уже отсортирован, отсортирован по убыванию, ответ в самом начале, ответ в самом конце.
- **Строка**: пустая, из одного символа, из одного повторяющегося символа, палиндром.
- **Ответ**: «ответа нет» (−1, `NO`), несколько правильных ответов, ответ больше 2³¹ или 2⁶³.
- **Отрезки и интервалы**: касаются концами, вложены, совпадают.

Один приём особенно полезен: задайте себе вопрос «что будет, если ответ — это самый первый или самый последний элемент?». На нём ломаются циклы, которые обновляют ответ не в том месте.

### Шаг 3. Стресс-тест в одном файле

Стресс-тест — сравнение вашего решения с медленным, но очевидно правильным перебором на тысячах маленьких случайных тестов. Удобнее всего держать всё в одном файле: решение и перебор — функции, которые принимают вход строкой и возвращают ответ строкой.

Пример: найти максимальную сумму подотрезка массива. Быстрое решение ниже содержит ошибку, которую примеры из условия обычно не ловят.

```python
import random


def fast(inp):
    a = list(map(int, inp.split()))[1:]
    best = cur = 0
    for x in a:
        cur = max(x, cur + x)
        best = max(best, cur)
    return str(best)


def slow(inp):
    a = list(map(int, inp.split()))[1:]
    n = len(a)
    return str(max(sum(a[i:j + 1]) for i in range(n) for j in range(i, n)))


def gen():
    n = random.randint(1, 5)
    a = [random.randint(-5, 5) for _ in range(n)]
    return f"{n}\n{' '.join(map(str, a))}\n"


random.seed(1)
for it in range(10000):
    t = gen()
    if fast(t) != slow(t):
        print("Контрпример:")
        print(t, "быстрое:", fast(t), "перебор:", slow(t))
        break
else:
    print("Расхождений нет")
```

За доли секунды стресс-тест найдёт контрпример — с этим `seed` это `3` / `-5 -5 -5`: все числа отрицательные, правильный ответ −5, а быстрое решение возвращает 0. Ошибка — в начальном значении `best = 0`: оно означает «пустой подотрезок», а пустой в этой задаче запрещён. Исправление — `best = a[0]`.

Три правила хорошего стресс-теста:

1. **Маленькие тесты.** n от 1 до 5–6, значения от −5 до 5. Контрпример находится быстро, и его можно проверить глазами. Большие случайные тесты ловят ошибки хуже: краевые ситуации в них встречаются редко.
2. **Перебор — максимально простой.** Никаких оптимизаций: если перебор тоже ошибается, стресс-тест бесполезен. Для задач «найти лучшее» — перебор всех вариантов, для задач на моделирование — буквальное моделирование.
3. **Фиксированный `random.seed`.** Тогда найденный контрпример воспроизводится при повторном запуске.

Если ваше основное решение уже написано как программа, читающая `sys.stdin`, оберните его: перенесите тело в функцию `solve(data)` и в конце файла вызывайте `print(solve(sys.stdin.read()))`. Для стресс-теста импортируйте `solve` напрямую — это быстрее, чем запускать процессы через `subprocess`.

### Шаг 4. Уменьшите контрпример

Если стресс-тест нашёл тест из 6 чисел, попробуйте уменьшить генератор до `n <= 3` или диапазон до 0–2 и запустить снова. Самый маленький контрпример обычно сразу показывает, какой случай не учтён: «один элемент», «все равны», «ответ в конце».

### Шаг 5. Отладочный вывод — в stderr

Если нужно посмотреть промежуточные значения, печатайте их в поток ошибок:

```python
import sys

print("debug:", cur, best, file=sys.stderr)
```

Проверяющая система сравнивает с эталоном только стандартный вывод, поэтому такая строка не превратит ответ в WA, если вы забудете её удалить. Но она тратит время — перед отправкой отладку всё равно лучше убрать.

`assert` проверяет то, во что вы верите: `assert 0 <= lo <= hi < n`. Если условие ложно, программа падает с RE. Иногда это полезнее WA: вердикт RE на тесте 7 точно говорит, что предположение неверно именно на этом тесте.

### Шаг 6. TL — проверьте скорость на максимальном тесте

Перед отправкой задачи с большими ограничениями сгенерируйте максимальный тест и замерьте время:

```python
import random

n = 2 * 10**5
with open("big.txt", "w") as f:
    f.write(f"{n}\n{' '.join(str(random.randint(-10**9, 10**9)) for _ in range(n))}\n")
```

и в терминале: `time python3 solution.py < big.txt > /dev/null`. Если локально больше половины лимита — на сервере почти наверняка будет TL. Кроме случайного теста стоит проверить худший: для сортировки — уже отсортированный массив, для хеш-таблиц — много одинаковых ключей, для рекурсии — «цепочка» максимальной глубины.

### Как это связано с секцией

На технической секции IWO код не запускается, поэтому стресс-теста там нет, но первые два шага остаются. В [статье Яндекса об алгоритмических секциях](https://yandex.ru/jobs/interview/algorithms) последний шаг решения — проверить код на примерах. Хороший ответ на вопрос интервьюера «как вы протестируете решение?» — это список из шага 2 применительно к задаче: «пустой массив, один элемент, все отрицательные, ответ в конце».

### Практика

Задачи этого модуля в тренажёре, на которых стоит потренировать стресс-тест: у каждой есть очевидный перебор.

1. [«Запросы за последние 3 секунды»](#/iwo/contest/recent-requests) — перебор: пересчитать все прошлые запросы.
2. [«k-е по величине в потоке»](#/iwo/contest/kth-largest-stream) — перебор: сортировать всё после каждого числа.

## Самопроверка

### Что выведет код?
```python
def fast(a):
    best = cur = 0
    for x in a:
        cur = max(x, cur + x)
        best = max(best, cur)
    return best

print(fast([-3, -1, -2]))
```
- [ ] `-1`
- [x] `0`
- [ ] `-6`
- [ ] `-3`
> Начальное `best = 0` соответствует пустому подотрезку. Если все числа отрицательные, правильный ответ −1, а функция вернёт 0 — именно такой тест находит стресс-тест.

### Решение получило WA на тесте 23, все примеры проходят. С чего эффективнее всего начать?
- [ ] Отправлять небольшие исправления, пока не пройдёт
- [ ] Переписать решение с нуля другим способом
- [x] Прогнать краевые случаи вручную, затем стресс-тест с перебором на маленьких тестах
- [ ] Проверить скорость ввода
> Посылки наугад тратят время и штрафные попытки. Краевые случаи и стресс-тест находят конкретный тест, на котором решение ошибается.

### Почему в стресс-тесте используют маленькие n и маленькие значения?
- [ ] Потому что большие тесты проверяющая система всё равно не использует
- [ ] Так быстрее работает `random`
- [ ] Маленькие тесты нужны только для поиска TL
- [x] Краевые ситуации (повторы, один элемент, все равны) на маленьких тестах встречаются часто, перебор успевает, а контрпример видно глазами
> При значениях от −5 до 5 одинаковые числа и нули выпадают постоянно, а на случайных числах до 10⁹ — почти никогда.

### Куда печатать отладочный вывод, чтобы случайно не получить WA?
- [ ] В стандартный вывод, но в конце
- [x] В `sys.stderr`
- [ ] В файл `output.txt`
- [ ] Через `input()`
> Проверяющая система сравнивает только стандартный вывод. Поток ошибок в сравнении не участвует, хотя время на вывод всё равно тратится.

### Решение локально на максимальном тесте работает 0,9 с при лимите 1 с. Что ожидать на сервере?
- [ ] OK — укладывается
- [x] Высокий риск TL: сервер может быть медленнее, а худший тест — тяжелее случайного
- [ ] ML
- [ ] Ничего нельзя сказать
> Запас нужен: скорость машин разная, а ваш случайный тест может быть не худшим. Если локально больше половины лимита, решение стоит ускорить.

## Вопросы на собеседовании

### Как вы протестируете своё решение?
Назвать конкретные тесты для этой задачи, а не «на разных данных»: минимальный вход, все элементы одинаковые, ответ в начале и в конце, отрицательные числа, «ответа нет», максимальный размер для проверки скорости. Затем прогнать код вручную на одном маленьком тесте, проговаривая значения переменных. В реальной разработке — ещё сравнение с простым эталонным решением на случайных тестах.

### Что такое стресс-тестирование?
Сравнение быстрого решения с медленным заведомо правильным на большом числе случайных маленьких тестов. Нужны три части: быстрое решение, перебор и генератор тестов. Как только ответы расходятся, у вас есть конкретный контрпример, на котором ошибку легко найти.
